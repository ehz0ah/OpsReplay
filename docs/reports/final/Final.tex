{\small\textbf{Summary.} OpsReplay is a Software-as-a-Service for practising
production incident response. Each learner gets a dedicated, deliberately
broken cloud environment running real services, investigates it with ordinary
tools in a browser terminal, repairs it, and then reviews an evidence-based
debrief and a synchronised playback of the attempt. The prototype runs on AWS
(CloudFront, Cognito, API Gateway, Lambda, DynamoDB, S3, ECS Fargate,
EventBridge) and was deployed and tested end to end in bounded campaigns.
Code: \Repo.\par}

\section{Motivation and Business Case}
\textbf{Theme: cloud-based production-engineering education.}

\subsection{Problem Statement}
Students and junior engineers rarely get to practise responding to a
production failure before they are responsible for a live service. Postmortems
explain what happened, but reading one does not require the reader to choose
which evidence matters, form a hypothesis under uncertainty, or test a recovery
decision whose consequences can make things worse. In real incidents, an
attempted fix can provide temporary relief, cause a new outage, or delay
recovery. The skill we target is therefore \emph{diagnosis plus judgement}:
finding the cause from incomplete signals and recovering safely.
Google's \emph{Wheel of Misfortune} trains this through facilitated team drills
that re-enact past incidents~\cite{sre}, but such drills need a facilitator,
a team and preparation time.

\subsection{Purpose, Target Users and Value}
OpsReplay turns this practice into an individual, on-demand web service.
Its primary users are computer science students and junior software, DevOps,
platform and site reliability engineers; a secondary market is course
instructors and bootcamps who want a ready-made lab. It has three modes:
\begin{itemize}
  \item \textbf{Challenges} (core): a live, isolated environment with one planted
  misconfiguration. Learners use a root shell and real tools (\texttt{curl},
  \texttt{dig}, \texttt{ss}, logs, config files). Traffic keeps flowing, so
  failures accumulate while the fault remains, and careless actions cause real
  outages. An independent monitor decides recovery.
  \item \textbf{Learn}: curated, team-written summaries of documented incidents
  with lessons and links to official reports.
  \item \textbf{Code Review}: learners flag risky lines in a diff and compare
  them with reviewed reference findings.
\end{itemize}
After a Challenge, learners get a debrief (root cause, causal chain, evidence
they found or missed, harmful actions, recommended recovery) and can replay
their terminal session beside the recorded metrics, or retry in a fresh
environment without overwriting the first result.

\subsection{Changes since the Preliminary Report}
The product follows the preliminary design (real services in per-attempt
Fargate containers, an independent monitor, debrief, playback, freemium).
Changes: terminals now enter through a CloudFront edge with WAF, a VPC origin
and an \emph{internal} load balancer instead of a public load balancer behind
Route 53; results report score components instead of one combined score; two
Challenges were published while the Hard one stayed a draft; the assistant
covers Challenges only (Code Review chat was deferred); and the 10/50/100-session
load tests, warm pool and multi-model LLM comparison were not done
(Section~\ref{sec:eval}).

\section{Business Model}
\subsection{Freemium Offer}
\begin{itemize}
  \item \textbf{Free}: a complete sample of every mode, including the Easy
  Challenge with full debrief, playback and fresh retries, so a learner
  experiences the core value before paying. Sessions last 20 minutes.
  \item \textbf{Pro} (proposed S\$12/month): currently the Medium DNS Challenge and a
  Pro lesson, growing into the planned library of Medium/Hard Challenges and Pro
  Code Reviews, plus 30-minute sessions. Entitlements are
  enforced on the server, not just hidden in the interface.
  \item \textbf{Institutional}: Pro seats licensed to a class or cohort (future).
\end{itemize}
The price is benchmarked against SadServers (US\$9--11/month for Pro
tiers~\cite{sadservers}); it is a hypothesis that still needs willingness-to-pay
testing. The prototype implements accounts, plans and a time-limited
``demo Pro'' grant, but deliberately collects no payment.

\subsection{Unit Economics}
Each Challenge attempt runs its own Fargate task (1~vCPU, 2~GiB), costing
US\$0.0616 per hour at Singapore list prices~\cite{aws-fargate}; in our hosted
tests an attempt averaged about 11 minutes from image pull to stop, or about
US\$0.011 of compute. An assistant reply cost about US\$0.0004 in tokens.
Variable cost is therefore small; the dominant cost at small scale is
\emph{idle shared infrastructure} (Gateway task, internal load balancer, VPC
interface endpoints), about US\$97.8 (S\$132) per month~\cite{aws-vpc,aws-alb}.

Assumptions (planning FX S\$1.35/US\$1): a Pro user consumes 6 Challenge-hours,
US\$0.30 of assistant use and US\$0.15 of API/storage per month; each subscriber
subsidises five active Free users (0.5 hours plus US\$0.075 of assistant and API use each); future card fees are
4.1\% + S\$0.50~\cite{stripe}. Variable cost per subscriber is then S\$1.82 and
contribution S\$9.19. Monthly fixed cost is S\$972 (S\$132 shared infrastructure,
S\$40 other services, S\$600 content and support, S\$200 acquisition).

\subsection{Cloud versus On-premise Hosting}
\label{sec:onprem}
\textbf{Equivalent service.} A fair comparison must host the \emph{same}
service, not merely run the three container images on a server. An on-premise
OpsReplay would need: HTTPS ingress and static hosting; an identity service with
verified email; a transactional database with conditional writes (for
duplicate-safe requests); a private object store with backups for recordings;
an isolated container scheduler with per-attempt networking and confirmed
cleanup; durable timers and retry workers; and logging, alerting and secrets
management. The code calls AWS SDKs directly, so a port also needs adapter work.

\textbf{Model.} We model one small server sized for two simultaneous attempts
plus the platform, against $H$ total Challenge-hours per month (all monetary
values S\$/month, before GST):

\midrule

Challenge compute per hour $H$ & $0.0832H$ & Power, 100 W $\times$ 1.4 at S\$0.2859/kWh & 29.22\\
API, identity, storage, logs & 40.00 & Network, backup, maintenance & 100.00\\
Operations, 2 h at S\$30 & 60.00 & Operations, 6 h at S\$30 & 180.00\\

\midrule
\textbf{Total} & $232.07+0.0832H$ & \textbf{Total} & 470.33\\

Electricity uses the SP Group Q4~2026 tariff~\cite{sp-tariff}; the S\$4,000
server is a sensitivity input informed by local retail listings for entry
servers (S\$3,777--4,956)~\cite{host-listing}, not a quote. Operator time is
valued at S\$30/hour.

At $H=50$, 400 and 1,200 Challenge-hours per month, cloud costs S\$236, S\$265
and S\$332, against S\$470 on-premise, or S\$300 if both need equal operator
time and no port work.

\textbf{Justification.} For OpsReplay's demand profile, cloud is the better
choice, but not because it is unconditionally cheaper:
\begin{itemize}
  \item \emph{Bursty demand.} Usage arrives as class-sized bursts around
  assignments, not a steady load. Fargate scales to many parallel attempts and
  costs nothing when idle; a server sized for two attempts cannot absorb a
  30-person class, and one sized for the peak sits idle most of the month.
  \item \emph{Isolation.} Learners get root shells. Fargate gives each attempt
  its own kernel boundary, private networking and no cloud credentials; a shared
  Docker host isolates root users less strongly.
  \item \emph{Availability and operations.} DynamoDB and S3 are multi-AZ
  managed services; a single non-redundant server is a single point of failure,
  and backups are not failover.
\end{itemize}
On-premise becomes competitive when an institution already owns qualified
hardware and staff: with equal operator effort and no port work, it is cheaper
above roughly 821 Challenge-hours per month. In the base case the crossover
(about 2,864 hours) exceeds the two-attempt server's capacity (1,460 hours), so
it is not reachable. The model's assumptions (labour, server price, power draw)
are not measurements and are the main sources of uncertainty.

\section{Architecture and Implementation}
\subsection{User Journey}
\noindent\begin{minipage}[t]{0.56\linewidth}\vspace{0pt}
A learner browses the catalogue (Figure~\ref{fig:catalogue}), reads a public
briefing that lists the services and where their logs and configuration live
(without revealing the fault), signs in and starts the attempt. The workspace
shows an alert, a browser terminal and a live telemetry panel (request rate,
errors, latency). A notice explains that leaving the page does not pause the
incident. Once the monitor confirms sustained recovery, or the time limit
passes, the attempt ends and the learner sees the debrief, playback and a retry
option. History keeps every saved result.

Each Challenge is a versioned container image with a small service stack under
a process supervisor, plus one planted misconfiguration, described by a JSON
manifest (traffic journeys, validators, traps, hints, debrief content).

passes, and traps are detected from real effects (an outage observed by the
monitor shortly after a risky command), not by matching expected commands.

Figure~\ref{fig:arch} shows the deployment, defined in AWS CDK (TypeScript).
\textbf{Web and identity:} the React single-page app is served from private S3
through CloudFront; Cognito handles verified-email sign-up and PKCE sign-in.
\textbf{API:} a Regional API Gateway REST API routes to one Lambda function per
action (start, end, ticket, debrief, playback, review, assistant, etc.), each
with its own role, timeout and concurrency limit. REST was chosen over the
cheaper HTTP API because it supports response streaming for assistant replies.
\textbf{State:} DynamoDB stores sessions, request receipts, timelines, review
submissions and conversation turns, all read by key; large recordings go to
private S3. \textbf{Environments:} starting an attempt calls ECS
\texttt{RunTask} with a task definition pinned to image digests. The task holds
the challenge container (services plus a private terminal server) and a separate
monitor container (traffic generator, metrics, validators, file captures).
\textbf{Terminal path:} browser WebSockets enter a CloudFront distribution
with WAF, reach an internal load balancer through a VPC origin, and land on the
Gateway service, which validates a short-lived ticket, proxies the terminal and
records everything. \textbf{Lifecycle:} ECS events and EventBridge Scheduler
drive readiness, deadlines, abandoned-session sweeps and reconciliation.

\subsection{Session Lifecycle and Reliability}
An attempt moves through
\emph{admitted $\rightarrow$ provisioning $\rightarrow$ ready $\rightarrow$
outcome fixed $\rightarrow$ recording drained $\rightarrow$ task stopped
$\rightarrow$ result saved}. Key design choices:
\begin{itemize}
  \item \textbf{Duplicate-safe requests.} Before any side effect, the start
  handler saves, in one DynamoDB transaction, a request receipt, a one-active-attempt
  lock, the session record and the exact launch arguments. A retried or
  reloaded request reuses the same receipt and ECS launch identity, so a lost
  response never launches a second task or records a second result.
  \item \textbf{Single outcome.} The first valid outcome (recovered, time limit,
  learner ended, abandoned) fixes one cutoff; later end requests return it.
  \item \textbf{Stale-worker safety.} Lifecycle events are treated as hints:
  workers re-read state, and conditional writes reject late timers, old
  generations and overlapping workers.
  \item \textbf{Confirmed cleanup.} The result is finalised only after the task
  stop and schedule deletion are confirmed, so no environment is left running.
  \item \textbf{Terminal resilience.} The shell survives browser disconnects and
  Gateway replacement; a reconnect resumes it.
\end{itemize}

\subsection{Recording, Debrief, Scoring and Playback}
The Gateway records terminal bytes, timestamped monitor measurements and
watched-file captures \emph{outside} the learner's writable environment, as
checksummed pages in S3. Terminal output is never trusted to decide recovery;
only the monitor does. The debrief is derived deterministically from the
pinned Challenge manifest and the recorded evidence: root cause, causal chain,
key evidence observed or missed, harmful actions with the outages that
followed, and the recommended recovery. We deliberately avoided over-claiming:
mentioning a file path is not counted as reading it, and a command preceding
an outage is shown as ``possibly harmful'', not proven causal. Instead of an
opaque weighted score, the result reports its components: time to recovery,
failed user requests, command count, number and duration of self-inflicted
outages, and hint/assistant use. Incomplete recordings get no score. Playback
replays the terminal recording in sync with the telemetry, with markers for
commands and key evidence; retries run in a fresh task and never alter the
first result.

\subsection{Learn and Code Review}
Learn entries are Markdown with metadata; Free lessons are built into static
assets, while Pro lessons stay in private S3 and are returned only after an
entitlement check. Code Review shows source context with selectable lines and
inline comments. Drafts survive refresh. Submission matches flagged lines
against authored reference ranges deterministically and reports found and
missed issues with explanations; written concerns are shown beside the
reference but not graded.

\subsection{Optional AI Assistant}
In a Challenge, the assistant explains recent evidence and may propose one
shell command through a typed \texttt{propose\_command} tool. Its context is
limited to public service information, completed commands and output, visible
metrics, released hints and recent turns; the planted fault, validators and
unreleased hints never enter the prompt. A proposal runs only after the learner
confirms the exact text, the Gateway checks ownership and expiry, and the shell
input buffer is empty; disruptive commands are flagged with a caution. The
assistant never owns state, recovery or scoring, its use is recorded, and
every Challenge can be completed with it disabled or failing. Replies stream
through the REST API, and each turn is guarded by a request receipt so a retry
never calls the provider twice.

\subsection{Security and Isolation}
Challenge tasks have no IAM role, run in private subnets with no internet
route, and accept traffic only from the Gateway. Every read and mutation checks identity, ownership and entitlement;
public API responses use explicit projections defined in JSON Schema/OpenAPI
contracts. Images are pinned by digest and must pass an Amazon ECR vulnerability
scan gate before any deployment is activated.

\section{Evaluation}
\label{sec:eval}
Each result below is tied to a source revision, workload and environment; all
hosted tests ran in \texttt{ap-southeast-1} in bounded, time-boxed deployments
that were torn down afterwards.

\subsection{Scenario Validity and Repeatability}
Automated image suites check, for each Challenge, that the fault is present at
start, validators fail before the reference fix and pass after it, and each
trap produces the stated outage. Twenty repeats of the Challenge suite and
twenty of the Monitor suite per incident (80 suite runs) all passed with
unchanged image IDs. The repository has 160+ test files across the API,
Gateway, Monitor, content, web and infrastructure, run by CI (nine jobs) on
every pull request.

\subsection{Hosted Functional and Reliability Tests}
Two hosted campaigns (29 October and 1 November) exercised the full product
with test learners. The 1 November campaign ran six attempts, at most two
concurrent, with one Gateway. The results are summarised in the table below.
Testing also found real problems. (1) Replacing the Gateway disconnected
the heartbeat of a second, concurrent attempt, which then ended as
\emph{abandoned}: a Gateway replacement can end other learners' active
attempts, a limitation that needs a grace period or multiple Gateways.
(2) Four reconciliation errors (mis-filtered Gateway service events and an
outcome read race) were addressed in PR~\#139 with regression tests, not yet
re-run on AWS. (3) Two learner-visible bugs were fixed in PR~\#144: a successful
Challenge could show a terminal error before its outcome reached the browser,
and the browser rejected the assistant's ``unavailable'' fallback response
because it was missing from the public error contract.

\subsection{AI Assistant}
Six synthetic Challenge situations were each run three times against the
production adapter (19 attempts: 18 completed, 1 failed). Completed replies had
p50/p95 latency of 4.6/6.0~s. Rubric review found a relevant command proposal
in 18/18 replies, accurate teaching in 17/18, at least one unsupported factual
claim in 4/18, and no destructive proposal. Two full deployed streams completed in
8.6~s and 6.6~s (the second returned only a command proposal, so the saved
fallback text was shown); the confirmed proposal was accepted exactly once even
when the confirmation was repeated. Total token cost for all 24 provider calls was about
US\$0.01. Prompt changes followed to reduce unsupported claims.

\subsection{Security Gate}
On 1 November the Gateway and Monitor images had no scan findings; each
Challenge image had 1 HIGH (glibc, accepted for this deployment model), 3 MEDIUM
and 3 LOW. A 4 November rebuild found three new SQLite HIGH findings, so the
gate correctly blocked activation; the team rebuilt SQLite from a fixed source
(merged), and fresh registry qualification is the next step before redeploying.

\subsection{Measured Cloud Cost}
The six 1 November attempts used 4,010 Challenge-task seconds and 5,688 Gateway
seconds: an estimated US\$0.117 of Fargate compute at list prices, consistent
with AWS Cost Explorer's account data (US\$0.112). These figures exclude shared
networking, which dominates at this scale (Section~\ref{sec:onprem}).

\subsection{User Evaluation}
\textbf{Protocol.} A formative pilot with 5--10 students or junior engineers
compares the full interactive workflow (8 minutes investigating and repairing
plus 4 minutes of debrief and playback) with a static written explanation of the
other incident, with equal study time and equivalent causal information. Four
assignment sequences counterbalance condition and order; the assistant is off.
Before and after each condition, participants answer diagnosis and recovery
questions scored with a common 0--8 rubric, then a transfer question on a new
case. Short tasks cover Learn, Code Review and saved results, followed by the
System Usability Scale (SUS)~\cite{sus} and a brief interview. Participants use
pseudonyms; consent and raw data are kept outside the repository.

\section{Conclusion and Future Work}
OpsReplay delivers a working SaaS in which learners practise incident response
on real, isolated services and learn from an evidence-based debrief and
synchronised playback. The prototype demonstrates the full loop on AWS with
duplicate-safe lifecycle handling, confirmed cleanup, entitlement checks and an
optional, bounded AI assistant. Cloud hosting suits the bursty, isolation-heavy
workload, although idle shared infrastructure dominates cost at small scale.

Future work: (1) publish more Challenges, starting with connection exhaustion,
and a Pro Code Review set; (2) measure provisioning time and terminal latency
at class scale and add a warm pool before scheduled classes; (3) reduce idle
cost, for example by starting the Gateway and endpoints only around class
windows; (4) instructor features: cohorts, assignments and progress dashboards
for the institutional tier; (5) real payments and fair-use limits; and
(6) a larger learner study of learning transfer and retention.
